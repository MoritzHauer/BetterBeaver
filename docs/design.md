# Requirements and design decisions

Status: living document — **update this file whenever a plan adds, changes, or retires a requirement or decision.** It is the starting point for understanding the product; together with the referenced plan sections it is sufficient to re-implement the app from scratch on a different tech stack (everything here except the "Current tech stack" section is stack-agnostic).

Reading order for a newcomer: this file → [architecture.md](architecture.md) → [STATUS.md](STATUS.md) → the individual [plans](plans/) as needed.

## Product

BetterBeaver is a spaced-repetition learning app for arbitrary topics. Languages are the first vertical (Kyrgyz), but the core is topic-generic: a mushroom-ID or software-architecture topic must fit without core changes. It ships to real users — never design for a single user; multi-language seams (English glosses first) exist from the start.

## Requirements

### Functional

**Content model** (normative detail: [plan 0001 §Domain model](plans/archive/0001-content-schema-and-kyrgyz-slice.md), amended by plans [0006](plans/archive/0006-domain-lexicon.md) and [0008](plans/archive/0008-lesson-layer-and-exercise-polish.md)):

- **Domain** — a subject area (`language` or `general`) owning one canonical **lexicon**: dictionary entries (`lexeme` for languages, `concept` for general domains), thematic **families**, and typed symmetric **links** (synonym/antonym, related/contrast) authored on one side only.
- **Topic → Lesson → Unit** hierarchy. Units are daily-sized and own the actual content: **items** (learnables), **tasks** (exercises), **notes** (explanatory markdown). Lessons and units unlock sequentially, but any lock is skippable after a confirmation — **amended by [0025 §8](plans/0025-progression-engine.md)**: locks become opt-in, authored only where an earlier unit genuinely must come first, and the gate is "every word answered correctly once".
- **Items** are typed by `kind` — `lexeme`, `concept`, `sentence` (with optional Anki-style cloze markup), `pair` (near-homophones) — with all topic-specific data in the payload; the core never knows about languages. Lexemes/concepts live in the domain lexicon and are shared across topics (one SRS state per word); sentences and pairs are topic-owned. Dialogue "texts" are not a separate kind: a note (readable) plus per-line sentence items (drillable).
- All shipped content is **validated** against a closed list of referential-integrity and shape rules (dangling refs, ownership, id prefixes, per-type floors, …) — the classes lettered (a)–(s)+ across plans 0001/0002/0004/0006. Invalid content is a build error, surfaced as a developer-facing error screen.

**Study loop**:

- **Eleven task types**: recognize (MCQ), recall (self-graded), cloze (typed, per blank), matching (2–5 pairs), scramble, build (word bank with distractors), listen, dictation, shadowing, minimal-pair, picture. Grading is either **auto** (wrong → quality 2, correct → 4) or **self** (Again 2 / Hard 3 / Good 5). Contract per type: [plan 0002 §Task-type catalogue](plans/archive/0002-exercise-type-showcase.md), [plan 0005](plans/archive/0005-sentence-building.md). **Ranked by [plan 0025 §2](plans/0025-progression-engine.md)** (implemented 2026-09-01): `EXERCISE_LEVEL` gives every exercise a fixed 1–10 difficulty, identical for every learner and every Book, with `shadowing` unranked because nothing checks its answer. An exercise is not a task type — `recognize` is two exercises (comprehend at 2, produce at 4) and `write` is derived from lexeme/concept items with no task type at all — so `TASK_EXERCISES` maps what content can author onto the ladder. Ties are deliberate, so a Book with no audio has fewer options at a level rather than a hole in its ladder. `picture` is a **production** exercise: its MCQ answers are the target-language forms, not the English glosses it showed before, which put no foreign form on the screen at all.
- **SRS**: one **word level**, 0-10, per scheduling unit — **[plan 0025](plans/0025-progression-engine.md)** (designed 2026-08-31, scheduler implemented 2026-09-01), which supersedes plan 0022's ladder and plan 0001's SM-2 arithmetic. The level is stored in `SrsState.reps` (the field SM-2's repetition count and 0022's rung lived in) and answers three questions at once: how hard the next exercise may be (it shares its scale with `EXERCISE_LEVEL`), how long until the word returns (`REVIEW_PACES` is now an eleven-entry interval row per pace, indexed by level — Balanced `1, 1, 1, 2, 5, 8, 15, 30, 90, 365`), and how far along the learner is. Difficulty climbs through the first four levels while the word is still met daily; spacing takes over from level 5. Good advances one level, Hard steps back one, Again and every wrong auto-graded answer step back **two, floored at 0** — never a reset. Every outcome reads its interval off the resulting level; no branch pins a card to "tomorrow" independently of it. **One level per UTC day from level 4 up** (`levelDay` records the day the level last advanced): levels 1-3 are all recognition, so a new word climbs to level 3 in its first sitting, and the guard bites on the advance that would _arrive_ at production. The practice-only rule (a result advances state only if the unit is new or due) is unchanged at and above level 4 and relaxed below it, or that first-sitting climb could not happen. **Classic SM-2 is removed** — the level carries difficulty _and_ timing, and SM-2 has no concept of difficulty — so `SrsState.ease` is dead, kept only so older backups still import, and the Scheduler setting is gone. Cards written by either retired scheduler **migrate by interval** on their next grade (30 days becomes level 8, 1 day becomes level 1), so no due date moves. The **grade mappings** are untouched and still pinned by [plan 0001 §Learner state](plans/archive/0001-content-schema-and-kyrgyz-slice.md) — auto: wrong 2 / correct 4; self: Again 2 / Hard 3 / Good 5 — and re-implementations must reproduce them exactly. Scheduling operates on **scheduling units**, not items: a cloze blank schedules individually, a note schedules as one self-graded flashcard (which reaches Daily Review only when pinned — see the review queue below), everything else per item. Due dates are day-granular UTC.
- **Review queue per domain**, deduplicated across topics, pinned scheduling units first, then due-ascending. **Notes enter only when pinned** ([plan 0025 §13](plans/0025-progression-engine.md), implemented 2026-09-01): a unit's theory is reference material, read when it is needed, not a card to be drilled, so for notes Pin widens from "show me this first" to "include this at all" — which is the mechanism already, since pinning a note grades it `again` to make it due. Nothing migrates; existing note state is simply no longer read for queueing. Pinning targets the exact question shown (a matching board's several units together; every other kind, one unit), not a task's other, unrelated units — amended by the UI polish batch, 2026-07-25 (see [Design decisions](#design-decisions)). Reviews use recall presentation for lexemes/concepts/plain sentences; cloze blanks and pairs review as their auto-graded question — **amended for sentences by [plan 0022 §6](plans/0022-scheduling-and-review-flow.md)**: a due sentence unit renders as its authored `build`/`scramble`/`dictation` exercise when one exists, falling back to recall; lexemes and concepts keep the recall card, because their own tasks are all MCQ and would be a downgrade.
- **Progress**: unit completion is _derived_ (all tasks attempted at least once) — never stored. A per-domain daily **streak** (local calendar day, no freezes). Practice buttons at unit, lesson, and topic level (higher levels shuffle over unlocked children).
- **Hints**: cloze blanks get a reveal-the-English hint; build tasks hide the English prompt behind a hint button. Example sentences hide their translation until tapped.
- **Cross-unit recall** ([plan 0016](plans/0016-cross-unit-recall.md)): a unit can manually declare `recallUnitIds` — earlier units it leans on — surfacing a skippable "Remember: …" card per link on its Overview page. Tapping it samples up to 5 random tasks from the linked unit and runs them as a practice-only session (no SM-2 rescheduling, no completion effect either direction). A block-level complement to per-item SM-2 scheduling, not a replacement; purely author-declared, no recommendation engine.

**Vocabulary** ([plan 0004](plans/archive/0004-vocabulary-mode.md), [plan 0006](plans/archive/0006-domain-lexicon.md)):

- Browse the whole domain lexicon (search, grouped); create/edit/delete named word lists; a built-in undeletable "Saved words" inbox; shipped read-only families.
- **Learner-created entries** (not validator-checked, merged into the pool at load, full study/SRS/link parity with shipped entries).
- **Ad-hoc study** of any list/unit/family in learner-chosen modes (flashcards, MCQ, matching incl. dynamic 5-pair sampling, listening), with runtime floors replacing validator guarantees (e.g. ≥4 distinct display texts for MCQ).
- **Tap-to-lookup** on any target-language word on non-graded surfaces only (post-answer, vocabulary rows, notes) — best-effort: exact match, then longest ≥3-char prefix (works because Kyrgyz is suffixing); a miss offers "add this word", never silence. Popup shows entry, links, families, optional hand-authored compound breakdown, save action.
- **Read-aloud**: recorded audio asset if present, else on-device TTS when a local voice matches the domain's declared language; feature hides gracefully otherwise.

**Data**: all learner state (SRS records, attempted tasks, streaks, lists, user entries, pins) lives on the device; one-click JSON export and restore-style import are the durability floor until opt-in sync exists.

**Offline mode** (Settings, added 2026-07-26): an explicit learner switch that takes the app fully off the network — no content update checks, no database traffic of any kind. Downloaded Books, vocabulary, review and progress all keep working; the Library, content editing, feedback/votes and chat hide themselves while it is on, "Refresh content" is disabled (it is a re-download, and offline there is nothing to download from), and the foreground update re-check — content catalog and service-worker build alike — does not run. Distinct from invariant 3 below: offline-_first_ means the app survives losing the network, offline _mode_ means it never uses it. Out of scope: the service worker's own app-shell refresh, which the app can't gate without switching to `prompt` registration.

**Legal pages** (added 2026-07-31): the operator is based in Germany, so the app carries an **Impressum** (§ 5 DDG) and a **Datenschutzerklärung** (Art. 13 GDPR) as two in-app screens, linked from the cover screen and the My Books footer under those German labels — the § 5 test is "leicht erkennbar, unmittelbar erreichbar, ständig verfügbar", and the cover is the first screen of every session. The privacy page is normative about what actually leaves the device (GitHub Pages request logs, the launch-time catalog fetch, the public chat's device id + display name, author emails) and has to be re-checked whenever those code paths change. No consent banner: there is no analytics or tracking of any kind, and the app's device storage is strictly necessary under § 25 Abs. 2 TDDDG. Ledger obligations that are not code — Art. 28 DPAs with Supabase and GitHub, Art. 30 record of processing — sit with the operator. **Superseded in part the same day** by the no-public-deployment decision below, which parked the Impressum for want of a § 5 addressee — and **un-superseded when that decision was retired**: the app is served publicly again, the Impressum ships with a real ladungsfähige Anschrift, and `PrivacyScreen`'s "served by GitHub Pages" paragraph is true as written. The Datenschutzerklärung rewrite stood on its own merits throughout (the note it replaces was factually wrong).

~~**No public deployment**~~ — **retired; recorded 2026-08-21**, after the repo had already moved (this row was simply never updated): the app is served publicly at **[betterbeaver.de](https://betterbeaver.de)**, built and deployed from `main` by `.github/workflows/deploy.yml` onto GitHub Pages behind the custom domain (`apps/web/public/CNAME`), with `index.html` bouncing the bare `moritzhauer.github.io/BetterBeaver` URL at the real host so one build never serves two origins. What the retired decision demanded is what unblocked it: the Impressum is filled in with a real ladungsfähige Anschrift rather than placeholders, so the § 5 DDG addressee exists. The `adb reverse` / `mkcert` provisioning in the README stays — it is how an unreleased build gets onto a phone, which a public deploy does not replace. The original reasoning, kept because it is what any future host has to clear: the app is not served publicly by anyone. § 5 DDG would require a ladungsfähige Anschrift — the operator's home address — on a project that has exactly one user, so the GitHub Pages deploy was retired rather than accept that trade. Devices are provisioned from a local `vite preview` behind an `adb reverse` tunnel (README, "Install on your phone"), which keeps `localhost`'s secure context and therefore the full PWA install/offline path. Revisit when there are real learners: the exemption also disappears the moment the app is offered _geschäftsmäßig_, and the usual escape is a c/o address service or Zustellungsbevollmächtigter rather than a home address. Any future host must be either behind auth (Cloudflare Access and similar keep it non-public) or accompanied by a filled-in Impressum.

**Versioning** (added 2026-08-21, owner decision): releases are `0.MINOR.PATCH` — **MINOR is a major feature change, PATCH is a landed plan or a small iteration**, and the leading `0` is load-bearing: the app is in beta, and `1.0.0` is reserved for the deliberate act of saying it is not. This is plain SemVer read at 0.x, so nothing has to be explained to anyone reading the number cold. `apps/web/package.json`'s `version` is the **single source of truth**; `vite.config.ts` inlines it (plus `GITHUB_SHA`) through `define`, `src/version.ts` re-exports it behind a `typeof` guard for the contexts that define neither (vitest, `vite dev`), and About shows both. Version **and** commit, because an installed PWA runs whatever its service worker last cached — the version alone cannot identify a build, and a screenshot is usually all a bug report has. Nothing in the app's behaviour keys on the version: it is a label, not a compatibility gate (`CONTENT_SCHEMA_VERSION` is the gate, and it is deliberately separate). Starting point 0.1.0 — the plans that landed before it (0001–0022) are in `docs/CHANGELOG.md`, not in the number.

**Never a silent blank screen** (added 2026-08-21, after the hardware-back bug survived two fixes): three separate paths could leave the app showing nothing at all, and on the dark theme "nothing at all" is a black screen that a bug report cannot describe. All three now have to explain themselves. (1) **The app has URLs, and hardware back is ordinary navigation** — `route.ts` gives every screen a fragment route (`#/books/demo/lessons/l1/units/u1`, flags in the query) and `history-nav.ts` moves between them with `location.hash`, listening on `hashchange`. The History API is deliberately out of the navigation path: a real back press skips script-inserted `pushState` entries, which is what defeated five earlier attempts, while a fragment navigation is something the browser itself performs. Back at the first screen leaves the app. Deep links, shareable Book URLs and reload-keeps-your-place fall out of it; none of it is visible in the installed app, which has no address bar. This replaced four builds of a "back trap" (a dummy entry plus a `popstate` interceptor, variously gated on the screen and on `display-mode`), none of which ever received a single `popstate` on the owner's device. The likely reason is Chrome's history-manipulation intervention, which marks an entry pushed without user activation as skippable and skips it silently — unproven, since no desktop Chromium here reproduces the skipping, but the routing is what every SPA does and is the only shape the browser does not police. The two earlier versions each released some pop (any root screen; then a root screen when `display-mode: standalone` was not reported) and each was verified green in a desktop browser that agreed with them while the phone did not. The cost is real and accepted: back at the root does nothing, and in a browser tab the back button no longer leaves this one site. (2) An **error boundary** wraps the app — React 19 unmounts the whole root on an uncaught render error, so before this a crash and a navigation escape were the same black rectangle. (3) `main.tsx` renders **nothing until `initContentSource()` settles**, so its rejection path now renders a failure screen instead of an empty root. A fourth path was found by that instrumentation and closed the same way (2026-08-21): **`openContentDb` rejects rather than hanging** — and a stalled boot was exactly when the guard was needed on `blocked` and on a watchdog, since a promise that never settles is the one failure a `try/catch` cannot rescue. The rule behind all of them: _nothing on the boot path may wait without a bound, and nothing that guards the app may depend on the app having started._ Backing all of it: an on-device **nav diary** (`nav-diary.ts`, a capped `localStorage` ring buffer shown under About → Diagnostics, never sent anywhere) records boots, back presses and crashes — the evidence a screenshot of a black page cannot carry, and the thing whose absence made the first two attempts guesswork.

**Content authoring**: content is hand-curated data files in the repo, produced via a human-in-the-loop checklist workflow (`/ingest`, [plan 0007](plans/archive/0007-ingest-kyrgyz-manual.md)) — explicitly _not_ an automated extractor (source OCR too noisy; selection is pedagogy).

**Content backend & in-app editing** (designed by [plan 0012](plans/0012-content-backend-and-editing.md); steps 1–2 shipped 2026-07-19, step 3 written as implementer-ready specs in [specs/](specs/), of which the proposal flow shipped 2026-07-26): content moves out of git into a hosted backend (Supabase) as whole JSON documents per topic and per domain, served through the same `ContentSource`. Authors sign in via email magic link — **learners never need an account**. Per-document maintainers (topics _and_ domains) edit drafts in form-based screens and publish validated versions atomically with append-only history; drafts are **local-first** (amended 2026-07-20): edits autosave to the device and reach the server draft only through an explicit Sync action on the editor's root (book) view — or through publish — and signed-in authors get ✎ Edit entry points on the learner topic/lesson/unit screens, and (UI polish batch, 2026-07-25) on the question screen itself — routing to the specific item/lexicon-entry, or to the owning task for matching questions — that deep-link into the editor at that level; non-maintainer edits become full-document proposals a maintainer accepts into draft or rejects; any signed-in user can create a topic, which enters the public catalog only after admin approval. Learner clients cache content in IndexedDB and update **only on explicit user accept** (all-or-nothing validated set); the bundled content becomes a frozen first-run seed. Assets stay bundled until the post-handoff asset pipeline. Progress sync is designed (local-first wrapper store, pinned merge rules, same accounts, strictly opt-in) but not scheduled for implementation. ~~Per-document maintainers edit drafts in form-based screens~~ — **retired 2026-08-04 by [plan 0021](plans/0021-in-place-editing.md)**, which landed in full: editing happens on the learner screens themselves (`editing` is a flag on the Book/Lesson/Unit routes, `screen: "edit"` is gone), the Book and its lexicon are one invisible pair behind a single Publish, and `EditScreen`'s form tree — 2656 lines — is deleted. Everything else in this paragraph still holds; only the editing surface changed.

**Library & Books** (designed 2026-07-21, implemented 2026-07-22, [plan 0015](plans/0015-library-marketplace.md)): "Book" is the learner-facing and code-level name for what plans 0001–0014 call a Topic (`Domain` keeps its name — invisible plumbing). Learners browse a **Library** — a flat marketplace list of every published Book, live metadata only (title/description/icon/rating via the catalog view + a counts-only vote view) — and explicitly **Add** Books, which downloads the Book and its domain document into the cache; the home screen (**My Books**) shows only added Books. **Archive** keeps a Book on-device but out of the front list; **Remove** evicts its documents (progress always survives — SRS/attempted/streak state is never garbage-collected, so re-adding restores it). Catalog removal no longer deletes local content, and validation granularity is per Book (a broken Book is excluded and surfaced, never silently wiped). The onboarding Book is pre-added on first run from the bundled seed, which shrinks to just that Book — Kyrgyz becomes Library-fetched. Search/filter and cover images are deferred.

**Content feedback** (designed and implemented 2026-07-20, [plan 0014](plans/0014-content-feedback.md)): learners get thumbs up/down and a report action (error/explicit/spam/free-text feedback) at every content level, plus one public chat thread per topic. Learners stay account-free — feedback is keyed by a per-device id and a random display name (`AnonymBeaver######`, editable in Settings), never a Supabase Auth identity. Maintainers review reports and moderate chat (delete) inside the existing per-document `EditScreen`.

### Non-functional (the four invariants — normative: [architecture.md](architecture.md))

1. **Headless core** — all domain logic in platform-agnostic packages; apps are thin views.
2. **Content behind `ContentSource`** — the schema is the contract regardless of transport.
3. **Offline-first** — fully functional without network after first load (this is why network-backed TTS voices are rejected and all assets are precached).
4. **Privacy by default** — learner data stays on-device unless the user opts into sync; no telemetry.

Plus: WCAG AA contrast in both color modes, animation off under `prefers-reduced-motion`, touch targets ≥ 44 px, installable on a phone home screen.

## Current tech stack (the replaceable part)

pnpm TypeScript monorepo, strict mode. `packages/schema` (zod entities + validator), `packages/srs` (pure SM-2), `packages/engine` (sessions, queues, progress; owns the pinned interfaces), `apps/web` (Vite + React PWA; the only I/O: `localStorage` adapter, bundled-content adapter via `import.meta.glob`, browser APIs). Content is JSON/markdown under `content/`, validated at startup. Quality gate: `corepack pnpm check` — prettier, eslint (type-aware: `recommendedTypeChecked` with a project service, so floating/misused promises are caught, at ~14s instead of ~3s), `lint:cycles` (madge; import cycles are invisible to `tsc` and would only surface as a blank screen at runtime, so they get their own step), `tsc --noEmit` per package, vitest. Deployment: GitHub Pages from `main` (`.github/workflows/deploy.yml`, gated on the same `pnpm check`), served at betterbeaver.de. GitHub Actions runs `pnpm check` on every push to `main` as the deploy job's gate — that workflow is the only one in the repo, so a red check blocks the deploy but nothing checks a PR before merge. Rationale for these picks: [plan 0001 §Tech stack](plans/archive/0001-content-schema-and-kyrgyz-slice.md).

A re-implementation must keep: the domain model, the pinned SM-2 semantics and grade mappings, the validator rule classes, the task-type contracts, the four invariants, and the layering rule (no domain logic in the view layer). Everything else — build tool, UI framework, storage backend, package layout — is swappable.
