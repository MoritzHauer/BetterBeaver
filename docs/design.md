# Requirements and design decisions

Status: living document — **update this file whenever a plan adds, changes, or retires a requirement or decision.** It is the starting point for understanding the product; together with the referenced plan sections it is sufficient to re-implement the app from scratch on a different tech stack (everything here except the "Current tech stack" section is stack-agnostic).

Reading order for a newcomer: this file → [architecture.md](architecture.md) → [STATUS.md](STATUS.md) → the individual [plans](plans/) as needed.

## Product

BetterBeaver is a spaced-repetition learning app for arbitrary topics. Languages are the first vertical (Kyrgyz), but the core is topic-generic: a mushroom-ID or software-architecture topic must fit without core changes. It ships to real users — never design for a single user; multi-language seams (English glosses first) exist from the start.

## Requirements

### Functional

**Content model** (normative detail: [plan 0001 §Domain model](plans/archive/0001-content-schema-and-kyrgyz-slice.md), amended by plans [0006](plans/archive/0006-domain-lexicon.md) and [0008](plans/archive/0008-lesson-layer-and-exercise-polish.md)):

- **Domain** — a subject area (`language` or `general`) owning one canonical **lexicon**: dictionary entries (`lexeme` for languages, `concept` for general domains), thematic **families**, and typed symmetric **links** (synonym/antonym, related/contrast) authored on one side only.
- **Topic → Lesson → Unit** hierarchy. Units are daily-sized and own the actual content: **items** (learnables), **tasks** (exercises), **notes** (explanatory markdown). Lessons and units unlock sequentially, but any lock is skippable after a confirmation.
- **Items** are typed by `kind` — `lexeme`, `concept`, `sentence` (with optional Anki-style cloze markup), `pair` (near-homophones) — with all topic-specific data in the payload; the core never knows about languages. Lexemes/concepts live in the domain lexicon and are shared across topics (one SRS state per word); sentences and pairs are topic-owned. Dialogue "texts" are not a separate kind: a note (readable) plus per-line sentence items (drillable).
- All shipped content is **validated** against a closed list of referential-integrity and shape rules (dangling refs, ownership, id prefixes, per-type floors, …) — the classes lettered (a)–(s)+ across plans 0001/0002/0004/0006. Invalid content is a build error, surfaced as a developer-facing error screen.

**Study loop**:

- **Eleven task types**: recognize (MCQ), recall (self-graded), cloze (typed, per blank), matching (2–5 pairs), scramble, build (word bank with distractors), listen, dictation, shadowing, minimal-pair, picture. Grading is either **auto** (wrong → quality 2, correct → 4) or **self** (Again 2 / Hard 3 / Good 5). Contract per type: [plan 0002 §Task-type catalogue](plans/archive/0002-exercise-type-showcase.md), [plan 0005](plans/archive/0005-sentence-building.md).
- **SRS**: SM-2, with semantics, grade mappings, and expected sequences pinned in [plan 0001 §Learner state](plans/archive/0001-content-schema-and-kyrgyz-slice.md) — re-implementations must reproduce them exactly. **Interval arithmetic superseded by [plan 0022](plans/0022-scheduling-and-review-flow.md)** (designed 2026-08-05, implemented 2026-08-12): the default scheduler is an explicit interval ladder (`1, 5, 15, 30, 90, 180, 365`, last rung repeating) where Good advances a rung, Hard steps back one and re-asks tomorrow, and Again resets to rung 0, re-asks tomorrow and re-shows the card inside the current Daily Review. The rung rides `SrsState.reps` and `ease` is left untouched, so classic SM-2 remains selectable and switching is lossless in both directions; the grade mappings, `applyGrade`'s practice-only rule and day-granular UTC due dates are all unchanged. Scheduling operates on **scheduling units**, not items: a cloze blank schedules individually, a note schedules as one self-graded flashcard, everything else per item. First graded result schedules; answers on scheduled-but-not-due units are practice-only. Due dates are day-granular UTC.
- **Review queue per domain**, deduplicated across topics, pinned scheduling units first, then due-ascending. Pinning targets the exact question shown (a matching board's several units together; every other kind, one unit), not a task's other, unrelated units — amended by the UI polish batch, 2026-07-25 (see [Design decisions](#design-decisions)). Reviews use recall presentation for lexemes/concepts/plain sentences; cloze blanks and pairs review as their auto-graded question — **amended for sentences by [plan 0022 §6](plans/0022-scheduling-and-review-flow.md)**: a due sentence unit renders as its authored `build`/`scramble`/`dictation` exercise when one exists, falling back to recall; lexemes and concepts keep the recall card, because their own tasks are all MCQ and would be a downgrade.
- **Progress**: unit completion is _derived_ (all tasks attempted at least once) — never stored. A per-domain daily **streak** (local calendar day, no freezes). Practice buttons at unit, lesson, and topic level (higher levels shuffle over unlocked children).
- **Hints**: cloze blanks get a reveal-the-English hint; build tasks hide the English prompt behind a hint button. Example sentences hide their translation until tapped.
- **Cross-unit recall** ([plan 0016](plans/0016-cross-unit-recall.md)): a unit can manually declare `recallUnitIds` — earlier units it leans on — surfacing a skippable "Remember: …" card per link on its Overview page. Tapping it samples up to 5 random tasks from the linked unit and runs them as a practice-only session (no SM-2 rescheduling, no completion effect either direction). A block-level complement to per-item SM-2 scheduling, not a replacement; purely author-declared, no recommendation engine.

**Vocabulary** ([plan 0004](plans/archive/0004-vocabulary-mode.md), [plan 0006](plans/archive/0006-domain-lexicon.md)):

- Browse the whole domain lexicon (search, grouped); create/edit/delete named word lists; a built-in undeletable "Saved words" inbox; shipped read-only families.
- **Learner-created entries** (not validator-checked, merged into the pool at load, full study/SRS/link parity with shipped entries).
- **Ad-hoc study** of any list/unit/family in learner-chosen modes (flashcards, MCQ, matching incl. dynamic 5-pair sampling, listening), with runtime floors replacing validator guarantees (e.g. ≥4 distinct display texts for MCQ).
- **Tap-to-lookup** on any target-language word on non-graded surfaces only (post-answer, vocabulary rows, notes) — best-effort: exact match, then longest ≥3-char prefix (works because Kyrgyz is suffixing); a miss offers "add this word", never silence. Popup shows entry, links, families, optional hand-authored compound breakdown, save action.
- **Read-aloud**: recorded audio asset if present, else on-device TTS when a local voice matches the domain's declared language; feature hides gracefully otherwise.

**Data**: all learner state (SRS records, attempted tasks, streaks, lists, user entries, pins) lives on the device; one-click JSON export and restore-style import are the durability floor until opt-in sync exists.

**Offline mode** (Settings, added 2026-07-26): an explicit learner switch that takes the app fully off the network — no content update checks, no database traffic of any kind. Downloaded Books, vocabulary, review and progress all keep working; the Library, content editing, feedback/votes and chat hide themselves while it is on, and "Refresh content" is disabled (it deletes cached documents before re-downloading, which offline would leave unrecoverable). Distinct from invariant 3 below: offline-_first_ means the app survives losing the network, offline _mode_ means it never uses it. Out of scope: the service worker's own app-shell refresh, which the app can't gate without switching to `prompt` registration.

**Legal pages** (added 2026-07-31): the operator is based in Germany, so the app carries an **Impressum** (§ 5 DDG) and a **Datenschutzerklärung** (Art. 13 GDPR) as two in-app screens, linked from the cover screen and the My Books footer under those German labels — the § 5 test is "leicht erkennbar, unmittelbar erreichbar, ständig verfügbar", and the cover is the first screen of every session. The privacy page is normative about what actually leaves the device (GitHub Pages request logs, the launch-time catalog fetch, the public chat's device id + display name, author emails) and has to be re-checked whenever those code paths change. No consent banner: there is no analytics or tracking of any kind, and the app's device storage is strictly necessary under § 25 Abs. 2 TDDDG. Ledger obligations that are not code — Art. 28 DPAs with Supabase and GitHub, Art. 30 record of processing — sit with the operator. **Superseded in part the same day** by the no-public-deployment decision below: with no publicly served instance there is no § 5 addressee, so the Impressum screen is parked unmerged rather than shipped with placeholder details. The Datenschutzerklärung rewrite stands on its own merits (the note it replaces was factually wrong) and only needs its hosting paragraph corrected before it lands.

**No public deployment** (added 2026-07-31): the app is not served publicly by anyone. § 5 DDG would require a ladungsfähige Anschrift — the operator's home address — on a project that has exactly one user, so the GitHub Pages deploy was retired rather than accept that trade. Devices are provisioned from a local `vite preview` behind an `adb reverse` tunnel (README, "Install on your phone"), which keeps `localhost`'s secure context and therefore the full PWA install/offline path. Revisit when there are real learners: the exemption also disappears the moment the app is offered _geschäftsmäßig_, and the usual escape is a c/o address service or Zustellungsbevollmächtigter rather than a home address. Any future host must be either behind auth (Cloudflare Access and similar keep it non-public) or accompanied by a filled-in Impressum.

**Content authoring**: content is hand-curated data files in the repo, produced via a human-in-the-loop checklist workflow (`/ingest`, [plan 0007](plans/archive/0007-ingest-kyrgyz-manual.md)) — explicitly _not_ an automated extractor (source OCR too noisy; selection is pedagogy).

**Content backend & in-app editing** (designed by [plan 0012](plans/0012-content-backend-and-editing.md); steps 1–2 shipped 2026-07-19, step 3 written as implementer-ready specs in [specs/](specs/), of which the proposal flow shipped 2026-07-26): content moves out of git into a hosted backend (Supabase) as whole JSON documents per topic and per domain, served through the same `ContentSource`. Authors sign in via email magic link — **learners never need an account**. Per-document maintainers (topics _and_ domains) edit drafts in form-based screens and publish validated versions atomically with append-only history; drafts are **local-first** (amended 2026-07-20): edits autosave to the device and reach the server draft only through an explicit Sync action on the editor's root (book) view — or through publish — and signed-in authors get ✎ Edit entry points on the learner topic/lesson/unit screens, and (UI polish batch, 2026-07-25) on the question screen itself — routing to the specific item/lexicon-entry, or to the owning task for matching questions — that deep-link into the editor at that level; non-maintainer edits become full-document proposals a maintainer accepts into draft or rejects; any signed-in user can create a topic, which enters the public catalog only after admin approval. Learner clients cache content in IndexedDB and update **only on explicit user accept** (all-or-nothing validated set); the bundled content becomes a frozen first-run seed. Assets stay bundled until the post-handoff asset pipeline. Progress sync is designed (local-first wrapper store, pinned merge rules, same accounts, strictly opt-in) but not scheduled for implementation. ~~Per-document maintainers edit drafts in form-based screens~~ — **retired 2026-08-04 by [plan 0021](plans/0021-in-place-editing.md)**, which landed in full: editing happens on the learner screens themselves (`editing` is a flag on the Book/Lesson/Unit routes, `screen: "edit"` is gone), the Book and its lexicon are one invisible pair behind a single Publish, and `EditScreen`'s form tree — 2656 lines — is deleted. Everything else in this paragraph still holds; only the editing surface changed.

**Library & Books** (designed 2026-07-21, implemented 2026-07-22, [plan 0015](plans/0015-library-marketplace.md)): "Book" is the learner-facing and code-level name for what plans 0001–0014 call a Topic (`Domain` keeps its name — invisible plumbing). Learners browse a **Library** — a flat marketplace list of every published Book, live metadata only (title/description/icon/rating via the catalog view + a counts-only vote view) — and explicitly **Add** Books, which downloads the Book and its domain document into the cache; the home screen (**My Books**) shows only added Books. **Archive** keeps a Book on-device but out of the front list; **Remove** evicts its documents (progress always survives — SRS/attempted/streak state is never garbage-collected, so re-adding restores it). Catalog removal no longer deletes local content, and validation granularity is per Book (a broken Book is excluded and surfaced, never silently wiped). The onboarding Book is pre-added on first run from the bundled seed, which shrinks to just that Book — Kyrgyz becomes Library-fetched. Search/filter and cover images are deferred.

**Content feedback** (designed and implemented 2026-07-20, [plan 0014](plans/0014-content-feedback.md)): learners get thumbs up/down and a report action (error/explicit/spam/free-text feedback) at every content level, plus one public chat thread per topic. Learners stay account-free — feedback is keyed by a per-device id and a random display name (`AnonymBeaver######`, editable in Settings), never a Supabase Auth identity. Maintainers review reports and moderate chat (delete) inside the existing per-document `EditScreen`.

### Non-functional (the four invariants — normative: [architecture.md](architecture.md))

1. **Headless core** — all domain logic in platform-agnostic packages; apps are thin views.
2. **Content behind `ContentSource`** — the schema is the contract regardless of transport.
3. **Offline-first** — fully functional without network after first load (this is why network-backed TTS voices are rejected and all assets are precached).
4. **Privacy by default** — learner data stays on-device unless the user opts into sync; no telemetry.

Plus: WCAG AA contrast in both color modes, animation off under `prefers-reduced-motion`, touch targets ≥ 44 px, installable on a phone home screen.

## Current tech stack (the replaceable part)

pnpm TypeScript monorepo, strict mode. `packages/schema` (zod entities + validator), `packages/srs` (pure SM-2), `packages/engine` (sessions, queues, progress; owns the pinned interfaces), `apps/web` (Vite + React PWA; the only I/O: `localStorage` adapter, bundled-content adapter via `import.meta.glob`, browser APIs). Content is JSON/markdown under `content/`, validated at startup. Quality gate: `corepack pnpm check` — prettier, eslint (type-aware: `recommendedTypeChecked` with a project service, so floating/misused promises are caught, at ~14s instead of ~3s), `lint:cycles` (madge; import cycles are invisible to `tsc` and would only surface as a blank screen at runtime, so they get their own step), `tsc --noEmit` per package, vitest. Deployment: none — see the no-public-deployment decision above. GitHub Actions runs `pnpm check` on push and PR (`.github/workflows/ci.yml`). Rationale for these picks: [plan 0001 §Tech stack](plans/archive/0001-content-schema-and-kyrgyz-slice.md).

A re-implementation must keep: the domain model, the pinned SM-2 semantics and grade mappings, the validator rule classes, the task-type contracts, the four invariants, and the layering rule (no domain logic in the view layer). Everything else — build tool, UI framework, storage backend, package layout — is swappable.
