3. **Asset pipeline** — Supabase Storage upload + cached learner delivery; unblocks the audio/picture task-type editors and new asset-backed content. Spec: [specs/0012-asset-pipeline.md](specs/0012-asset-pipeline.md), **revised 2026-07-30** after an owner grilling — the original was written before plans 0015/0017 and the `EditScreen` split, and three of its mechanisms are now deliberately reversed. Downloaded blobs live **inside the `CachedDocument` record** (the `PrivateBookRecord` shape), so Remove/`purgeUnmembered`/Refresh-content/Archive and accept atomicity all fall out of the existing per-document eviction with no new lifecycle code and no `DB_VERSION` bump; resolution **stays synchronous** through a boot-time object-URL overlay (`content/remote-assets.ts`, a near-copy of 0017's `private-assets.ts`) instead of the async `getAssetUrl` ripple through four screens, and the Cache API/Workbox route is dropped so private and remote assets share one mechanism; downloads are **eager and all-or-nothing per Book** at `addBook`/`acceptUpdate`, which is what keeps the offline promise literally true. An asset now has two names — a generated `${code}-<uuid>` stem (what content references) and a display name carried in the object key as `<stem>__<filename>`, since `slugPattern` forbids underscores and Supabase's `list()` returns only system metadata; the UI never shows a bare stem as a title. `AssetsManager` is **widened, not forked** (`AssetView[]` + `onAdd`/`onDelete`, private mode passing its existing `writeThrough`). Two hazards the eager download created and the spec now closes: deleting an asset the **published** document references is blocked (it would 404 during a stranger's Add and roll back the whole Book, invisibly to the maintainer, whose copy is already cached), and `scripts/export-content.ts` must download the `demo` Book's assets into `content/demo/assets/` — the seed is pre-added from the bundle and never fetched, so a remote-only ref there breaks the onboarding Book on a fresh offline install. No `docs/design.md` rows yet: the pipeline's decisions are recorded in the spec and graduate to the decision table when the code lands. **Sliced for delegation 2026-07-30** — the revised spec needs ~55k tokens of reading across ~11 files, over the budget `design.md` pins, so it ships as [0012-A read path](specs/0012-a-remote-asset-read-path.md) (landed: `CachedDocument.assets`, `content/remote-assets.ts`, the sync resolution chain — deliberately inert, nothing writes blobs), [0012-B download + validation + bucket](specs/0012-b-asset-download.md) and [0012-C upload UI + seed export](specs/0012-c-asset-editor-and-seed.md). **All three implemented 2026-07-30** via `implementer` subagents, `pnpm check` green on an independent re-run (312 tests, 3 skipped) — C adds `assetFolder`/`buildObjectName`/`uploadAsset`/`deleteAsset`, the widened `AssetsManager`, a maintain-mode Assets section gated on `!readOnly`, and the seed download pass. `ProposeEditScreen.tsx` is untouched by construction (proposers can't write: Storage RLS is maintainer-only). **Not yet browser-verified and not committed**, and the end-to-end live round-trip — upload through the editor, reference it, publish, add on a second device, play in airplane mode — is an owner-run step that has not happened, so nothing has ever actually travelled the pipeline. **`supabase/migrations/20260730000000_assets.sql` applied to the live Supabase project 2026-07-30** via the dashboard SQL editor — the project has no `supabase/config.toml`, so it has never been CLI-linked and `db push` would replay from statement 0. That migration was **amended before it was applied**: the spec originally said "read access comes from the bucket being public; add no select policy", which is wrong — a public bucket exempts only the public-URL download endpoint, while `list()` is a query against `storage.objects` and goes through SELECT RLS, so without an explicit `anon, authenticated` select policy every learner's asset listing returns `[]` while every local test still passes. **Live-verified 2026-07-30**: an anon-key `POST /storage/v1/object/list/assets` returns `[]` with HTTP 200 — bucket present, enumeration permitted, which is exactly what `listDocumentAssets` needs and what no local test can assert. Two further spec gaps were found and decided during 0012-B: `addBook` validated before it listed (a first Add of any Book referencing Storage assets would have failed on dangling refs — fixed with an optional `extraStems` on `buildMembers`), and validation buckets an asset by its `audio`/`img` folder while the runtime overlay buckets by `blob.type`, which agree only because slice C's upload must derive the folder from MIME (`assetFolder` is now the sole writer, so they cannot diverge). A third gap was decided during 0012-C: the Assets section originally ignored `readOnly` (`schema_version > CONTENT_SCHEMA_VERSION`) while the file's other four mutation surfaces are all gated on it — a maintainer on a stale build could have mutated live Storage for a document their client had just declared it couldn't safely reason about, and the delete guard leans on `assetReferences` understanding the published shape, which is exactly what schema skew puts in doubt. Now gated. **Two follow-ups tracked, neither done**: a seeded asset arriving with an extension outside `vite.config.ts`'s PWA `globPatterns` is silently not precached (the existing warning at `bundled.ts:53` names this class of bug), and the whole pipeline is still uncommitted, interleaved in one working tree with unrelated in-flight screen work — no file overlap, so a staged split is clean, but it gets harder the longer both sides grow.

**Proposal-only authoring access (2026-08-24)** — no plan doc; owner question ("how could I give you access to the books safely?"). Answered with the identity the backend already models rather than a new service: `scripts/author-auth.ts` resolves one of three identities in precedence order — `BB_AUTHOR_TOKEN` (+ anon key) → `SUPABASE_SERVICE_ROLE_KEY` → bare `SUPABASE_ANON_KEY` — and `pull-book.ts` / `propose-book.ts` take it from there. An **author-mode** identity is a signed-in account with no `admins` and no `maintainers` row: RLS lets it read the `catalog` view and insert its own `proposals`, and nothing else — it cannot publish (`publish_document` checks `is_maintainer`), cannot list (`set_listed` is admin-only), and cannot see an unlisted document (`documents_select` is maintainer-only, which is why both scripts read `catalog` in every non-service mode). Proposals now carry a real `author` instead of landing authorless, so they show under "My proposals" and are withdrawable — the wart `propose-book.ts`'s own header documented. `scripts/author-token.ts` (owner-side, service key) mints a **one-hour** access token for that account through the existing `admin/generate_link` flow, so the service key never leaves the owner's machine and nothing long-lived is ever handed over; `mintTestSession` gained an `email` parameter for it. Setup, the SQL to verify the account holds no grants, the loop and the two validation gaps it inherits are in `supabase/README.md` ("Authoring without a service key"). Long-lived access is the account's **refresh token** rather than a longer JWT: `author-auth.ts` exchanges it per run and writes the rotated token to `.bb-author.local` (git-ignored, 0600), which is then the live copy — an exported env var is spent after one run. Raising the project's JWT expiry was rejected as the alternative: it is project-wide, so it would lengthen every learner's session to lengthen one author's. Where that standing credential may live (machine you control: yes; a cloud environment's variables: against Anthropic's own guidance, no secrets store, readable by anyone using the environment) is in the same README section, along with the egress-allowlist requirement a cloud session hits first. Tier 2 — adding that account to `maintainers` for one document, which turns the same token into publish rights — is deliberately not done. Unverified against the live project: nothing here could be exercised from the session that wrote it (no backend credentials, by design).

- **"Refresh content" bricked every fetched Book (bug)** — the button was `clearCachedDocuments()` + reload, on `specs/0012-asset-pipeline.md`'s assumption that "the next sync re-downloads". Plan 0015 had since scoped syncing to _cached_ member documents (`memberCachedVersions` skipped a Book with no cached record), so after the wipe there was nothing left to scope to: the next check planned nothing, and every added Book except the seed-backed `demo` came back as a permanent "missing cached content" card. Firefox for Android has exactly this filed as [Fenix #25328](https://github.com/mozilla-mobile/fenix/issues/25328) ("the history from replaceState/pushState is not being honored when you press the back button, however, if you do `history.back()` then the URL will update correctly"), tracked at [bug 1603586](https://bugzilla.mozilla.org/show_bug.cgi?id=1603586).
